# 三国火纹游戏开发设计与执行提示词 v1.3

本提示词供开发 AI 在游戏项目中执行：使用现有三国美术资源，先交付可以从开场玩到结算的第一关，再逐步实现全流程。全文可复制到开发聊天；美术资源目录可通过 `ART_PACK_ROOT` 配置。

用户已确定技术栈为 **React＋TypeScript＋Canvas 2D**，地图采用 **完整底图＋独立逻辑网格＋交互物件层**。首版以正交方格表达玩法，不实现等距坐标转换。本文的首版范围、数值和平衡限制属于建议默认值，可直接用于原型；它们不代表用户已逐项确认或游戏已完成验证。

## 三、地图与占格方案

### 1. 三类数据分离

| 数据层 | 内容 | 约束 |
| --- | --- | --- |
| 视觉层 | 完整底图、可选前景、天气和光照 | 只负责显示，不决定通行 |
| 逻辑层 | 格子地形、移动代价、防御、回避、高度、阻挡、部署点与事件区域 | 战斗、寻路和AI的共同依据 |
| 实体层 | 单位、宝箱、门、桥、火焰等的状态、占格与显示资源 | 逻辑状态和视觉状态同步更新 |

首版使用 `plain_day` 的1024×768底图，正交网格16列×12行、格子64像素。坐标左上角为 `(0,0)`，`column` 向右、`row` 向下；只允许上下左右移动。保持图片比例，不把这张图硬拉成24×18格。

需要为192个格子逐一标注并保存地形、障碍及部署点。`collisionAuthored:false` 表示现成底图没有完成这项工作；给PNG盖上网格或自动按像素颜色分类都不等于标注完成。

### 2. 地图制作顺序

1. 叠加64像素网格，确认战场边界、桥头、道路、树林、建筑和主要交战区域。
2. 用可编辑JSON标注格子并设置出生点、目标和事件区域。建筑主体、深水、悬崖按规则阻挡；树冠的装饰覆盖不自动等于整个区域不可走。
3. 检查行走路线是否落在画面能理解的道路、桥面和空地内。视觉不合适的单格进行人工校准；局部整图无法支持可靠玩法时记录需返修区域，不允许角色踩着深水或屋顶行走。
4. 验证我方部署区到敌方和目标区的可达性；检查桥头连接、占格冲突、封闭区域以及路径与高亮范围一致性。
5. 输出有坐标与地形标识的检查图，再在真实游戏中逐条移动验证。

M1中的桥梁和建筑是静态地形，不可破坏。若以后把底图中已画死的桥、门、房屋改为动态物件，必须先有清除原物体后的底图或完整覆盖的状态补丁；仅在原桥上叠一层火焰不能实现桥梁消失。

树冠或屋顶需要遮住单位时，必须有独立前景及遮挡规则。没有前景素材时首版避开需要穿过其后方的路线，不把整张底图放到单位上层。

### 3. 地图协议与后续模块化

游戏地图使用稳定ID与版本，至少描述：网格宽高、格子尺寸、视觉资源、逐格地形、实体及占格、部署点、事件区域、胜负条件。地形定义集中保存各移动类型的代价、阻挡、防御与回避；高度首版均为0。

单位逻辑位置是整数格。图片脚底锚点和视觉偏移可独立设置，不能用图片边界反推占格。未来2×2单位移动时检查覆盖的全部格子、目标占位及路径每一步，不能只测锚点一格。

后续渲染可切换 `background` 与 `modular`，战斗内核继续读取同一份逻辑地图。模块图也可以预先烘焙成底图，同时保留可编辑图层与逻辑数据；M1只实现 `background`，不要求同时写第二套渲染器。

v2.2.0-preview中的大型高地目前只有图像包围范围，展示时约6×6格，未提供逐格高度、可行走顶面、悬崖阻挡和坡道连接。样板中的部分位置也未按整数逻辑格落点。它们暂作景观候选，不能据6×6画布直接设置“全部可走”或“全部挡路”。

图层拆分可以参考Tiled的图像层、瓦片层和对象层，但M1以JSON为权威地图数据，不强制引入编辑器转换流程。[Tiled图层文档](https://doc.mapeditor.org/en/stable/manual/layers/)

## 四、核心战斗规则

本节补齐原v1.2空缺的2.1。以下数值为首轮原型默认值，集中配置，不散落在组件和绘制函数中。它们用于建立可验证的规则，不声称已经完成平衡测试。

### 1. 属性与移动

基础属性：生命 `HP`、力量 `STR`、智力 `INT`、技巧 `SKL`、速度 `SPD`、幸运 `LUK`、防御 `DEF`、谋略抗性 `RES`、体格 `CON`、移动 `MOV`。另有等级、经验、策略点 `SP`、爆气槽、状态效果和所属阵营。

| 地形 | M1步行代价 | 防御加成 | 回避加成 |
| --- | --- | --- | --- |
| 平地、道路、静态桥面 | 1 | 0 | 0 |
| 林地 | 2 | 1 | 15 |
| 建筑主体、深水、悬崖 | 不可进入 | 不参与站立计算 | 不参与站立计算 |

进入目标格时支付移动代价；不能穿过敌军，可以穿过我方及友军，但不能停在任何已占用格。移动范围用带权最短路计算，推荐Dijkstra；路径预览、实际移动和AI使用相同的通行规则。

M1不启用控制区、斜向移动或移动后再移动。角色未提交攻击、道具或待机前，可撤销本次预移动；撤销不得消耗行动、道具或随机数。提交行动后不能通过取消菜单恢复行动次数。

### 2. 武器分类与相克

**剑克刀斧，刀斧克枪，枪克剑。** 优势方命中＋15、攻击＋1，劣势方命中－15、攻击－1；弓、计策、辅助不参与此三角。

这保证第一关中张飞的枪克制黄巾剑兵，关羽的刀斧受到剑兵克制。双股剑的“双剑外观”不自动获得两次攻击；攻击次数由追击或明确技能决定。

分开保存 `artWeaponId`、`visualFamily` 和 `combatFamily`。例如青龙偃月刀用美术分类 `blade`、战斗分类 `axe`，不修改原资源分类。法器素材中的 `magic` 也不代表所有谋士都有普通魔法轰炸能力。

普通近战范围1格；普通弓射程恰为2格，贴身不能攻击或反击。距离采用曼哈顿距离；M1不另加视线遮挡和高度射程规则，首关近战布局不依赖这些效果。技能的范围、目标关系和条件各自配置。

### 3. 计算公式

```text
AS = max(0, SPD - max(0, 武器重量 - CON))
Atk = STR + 武器威力 + 相克攻击修正 + 技能攻击修正
Damage = max(0, Atk - 目标DEF - 目标地形防御 - 目标防御状态修正)
Avoid = 2 × 目标AS + 目标LUK + 目标地形回避 + 目标回避状态修正
Hit = clamp(武器命中 + 2 × SKL + floor(LUK / 2)
            + 相克命中修正 + 技能命中修正 - Avoid, 0, 100)
Crit = clamp(武器暴击 + floor(SKL / 2) + 技能暴击修正 - 目标LUK, 0, 100)
暴击伤害 = Damage × 3
追击条件 = 自身AS - 对方AS >= 4
```

每次攻击使用一次0—99命中判定，命中后再做一次0—99暴击判定，随机值小于百分比即成功；不是隐藏的双随机命中。随机数来自可保存状态的带种子生成器。

顺序为发起者攻击 → 防守者若存活且武器射程合法则反击 → 满足速度差的一方若仍有合法攻击则追击一次。任一方败退后立即停止该次交战后续攻击；无反击能力的弓兵不能因速度优势贴身追击。

战斗预测与实际结算共用规则函数。预测显示伤害、命中、暴击、次数、反击情况和双方地形，不消耗随机数，不提前决定是否命中。命中为0时动画应回避；伤害为0不另造一次未定义的格挡概率。

### 4. 首关角色与平衡

为刘关张、普通剑兵和头目制作明确的初始属性与武器数值表。三兄弟使用标志武器外观，但首关数值按教学难度设定，不能仅因“神器”名称获得压倒性数值。

建议首关仅实现以下三个个人被动，效果写入配置；其他角色只登记特技名称与设计状态。

| 角色 | 特技 | M1默认效果 |
| --- | --- | --- |
| 刘备 | 仁德 | 我方阶段开始时，相邻我方或友军恢复2HP，不含自己，不超过最大HP |
| 关羽 | 威震华夏 | 当前HP不少于最大HP一半时，物理攻击命中＋5 |
| 张飞 | 当阳怒吼 | 当前HP不高于最大HP一半时，物理攻击＋2 |

伤药建议每人3次，每次恢复10HP，耗一次行动；M1只支持对自己使用。每场交战中存活且实际参与攻击的我方获得10经验，击败敌人再加20，每场只结算一次；100经验升级。提供前三人的成长率表，成长使用同一可保存随机系统，最大HP成长同步增加当前HP并受上限约束。

首关武器暂不消耗耐久，不实现武器熟练度。为无耐久状态使用明确数据表达；未来加入耐久时再定义损坏、反击与背包切换规则。

### 5. 回合与敌军AI

全局回合依次为我方 → 友军 → 敌军，无友军时跳过其阶段。一个完整循环后回合数加1；各阶段开始时仅重置该阵营的行动状态。

AI对每个存活且未行动的敌人：枚举可达落点与合法目标，优先可击败的目标，其次评估预期伤害与反击风险；无法攻击时沿可达路径接近目标，完全无路则待机。同分按稳定单位ID和坐标排序。不得瞬移、穿墙、读取玩家未来随机结果或重复行动。

进入胜负状态后停止AI和新的输入指令。玩家连点、按住确认、快进动画和切换标签页不能重复扣血或跳过回合。

## 五、差异化计策与爆气

本节保留完整游戏目标，M1仅需避免把相关字段与规则写死；从M2起按人物与剧情逐项实现。

### 1. 策略点与计策

谋士主要通过计策影响战场，消耗一次行动和个人策略点SP。SP是否恢复、每种计策消耗及状态持续时间由配置管理；原型可暂用每场重置、战斗内不自动恢复，后续平衡时再调整。

| 能力 | 必须表达的规则 |
| --- | --- |
| 火计 | 目标格满足干燥及可燃标签；产生有寿命的燃烧状态；扩散和伤害按回合结算 |
| 水计 | 目标在水域或与水域连接；影响范围与冲击效果由关卡配置 |
| 落石 | 需要山地或配置好的落石来源；伤害区域明确，不在任意平地召唤巨石 |
| 伊籍减防 | 射程1—2格，降低敌人防御，为物理输出创造条件 |
| 马良增益 | 在指定范围内提升我方或友军移动力或攻击力，持续时间及同类叠加规则明确 |
| 糜竺后勤仓库 | 相邻我方或友军可消耗自己的行动借用其背包道具；扣除糜竺库存；糜竺主动为队友用伤药则消耗糜竺行动 |

前置条件、扣费、目标选择、效果和失败原因统一由规则层校验。状态保存来源、持续时机和叠加方式，避免用浏览器秒数表示战棋回合。VFX只是状态的可视表现，关闭或快进动画不改变火势、伤害及持续时间。

张徵的道术、祝融的火神能力、敌方妖术师可另有明确的伤害技能；这不意味着诸葛亮、马良、伊籍等自动共享一套常规魔法攻击。

### 2. 爆气

- 虎牢关：刘关张仅在剧情事件中临时触发，离关清除临时资格。
- 虎牢关吕布：第三阶段进入专门的Boss状态，数值和行为由阶段配置改变，不污染永久角色模板。
- 长坂坡后：赵云与张飞通过剧情标志获得稳定爆气；首关不能提前开放。
- 赵云“七进七出”：爆气期间击杀可重置行动，首轮平衡建议每我方阶段最多重置2次；由该效果产生的击杀不能无限延长爆气或重复回充。
- 张飞“断桥咆哮”：明确范围、受影响阵营、威压状态和持续时机；桥梁是否断裂是独立关卡事件，不由技能动画擅自改图。

赵云个人特技和爆气名称重复时使用独立ID，避免同一击杀同时触发两次重置。被动的具体效果在实现该角色时另定；本轮上限为建议平衡值。

## 六、职业与内容配置

人物拥有专属纵向职业线，升级与转职分开处理；达到等级、获得剧情资格或外传道具后由玩家选择是否转职。二阶与三阶的等级门槛、等级是否重置等尚未确定，不应在M1硬编码。

逻辑职业、武器战斗类别、移动类型和小人模板独立配置。姜维从轻骑转卫士是否下马、黄忠的弓骑阶段如何映射素材，需要在对应阶段决定；不能只改职业显示名称而保留错误移动类型。

高顺二阶封顶，三阶明确为空。貂蝉、孟获前两阶显示名相同仍保留不同阶级ID，不能被去重。每个角色的个人特技、成长、招募条件、时期立绘与剧情可用性单独配置。

附录A的32人职业树和附录B的完整关卡大纲为后续内容依据。除首关范围内的内容外，不把未实现条目写成已解锁或已可玩。

## 七、程序架构与界面

### 1. 技术栈和职责

使用React＋TypeScript＋Canvas 2D，建议Vite构建。新建项目时选择当时可安装的兼容稳定依赖并提交锁文件；已有项目则优先复用依赖，不无故升级。运行时不调用在线AI服务。

- `core/`：纯TypeScript规则、状态、坐标、寻路、战斗结算、AI、随机数和存档数据。不得依赖React、DOM、图片加载或Canvas。
- `data/`：角色、职业、武器、地形、关卡、对话、资源映射和版本化规则配置。
- `render/`：地图、小人装配、镜头、特效、动作播放；把规则事件转换为表现。
- `ui/`：React界面，包括菜单、人物信息、地形提示、战斗预测、背包、对话和结算。
- `assets/`或静态目录：导入器生成的资源依赖及来源记录，不能重复手工维护整份美术清单。

目录按实际规模裁剪，不必先建立大量空文件。优先使用直接、可测试的函数和类型，不为M1搭建通用ECS、复杂插件系统或服务端。

核心接口应覆盖“合法移动查询、战斗预测、提交行动、结束阶段、序列化和恢复”。资源数据与游戏数值分别管理，不将美术清单当作角色数值数据库。

### 2. 状态和动画

交互状态至少区分：未选择、单位选择、预移动、行动菜单、目标选择、战斗预测、行动执行、敌军阶段、剧情、胜利、失败。

规则层在提交指令时校验并生成结果与事件；表现层按顺序播放移动、挥砍、命中和退场。逻辑结果只提交一次，动画回调不再扣一次血。快进、跳过动画及恢复焦点只改变表现进度，不能改变战果。

React按交互或规则事件更新面板，Canvas使用 `requestAnimationFrame` 绘制。动画计时、画布对象和资源缓存可通过ref保存；不能每帧把所有单位坐标写入React状态。清理事件监听和动画循环，避免开发模式重复挂载导致双倍执行。修改ref不会触发React重渲染，应通过明确的状态订阅刷新面板。[React useRef文档](https://react.dev/reference/react/useRef)

缓存不变的地图层与已解码图片，避免逐帧重新加载资源；处理Canvas实际尺寸、CSS显示尺寸和设备像素比，统一屏幕坐标到地图格子的逆变换。绘制关闭平滑采样，缩放保持比例，优先整数倍率，小窗口可使用镜头移动。[MDN Canvas性能与高分辨率画布指南](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas)

### 3. 交互与视觉目标

采用深蓝或暗红面板、暗金边框、清晰中文和克制的像素动画。地图是主要视觉区域，边角显示单位、地形和回合，选择目标时再展开双边战斗预测，避免用常驻大型表格遮住地图。

角色详情能看到头像、姓名、职业、HP、武器及相克类别；地形提示展示移动代价、防御和回避。已行动单位用变暗或小标识区分，选中和攻击范围高亮落在逻辑格内。

鼠标点击选择，右键或Esc取消，方向键移动光标，Enter确认。对话可先补全当前句、再进入下一句，支持跳过已读段落；菜单打开时不把同一次输入传给地图。资源加载中显示进度，失败显示可理解的错误信息。

使用真实动作和效果完成地图战斗，不只让静态单位卡片互相扣数字。M1不使用与原像素风格无关的emoji、渐变卡片或临时矢量人形替代正式素材。

### 4. 存档

M1可使用本地存储，保存版本号、关卡ID、回合与阶段、单位属性与位置、背包、经验、存活/入队状态、剧情标志、地图状态和随机数生成器状态。仅在我方可操作的稳定状态及战后结算保存；预移动和行动动画中不创建半完成存档。

读取时检查版本与完整性，错误存档应提示并保留原数据。读档后不能重复奖励经验、重复招募简雍或重复触发胜利剧情。不要把图片、DOM节点和计时器直接序列化。

## 八、开发顺序与验收

### 1. 执行顺序

1. 检查项目规范、当前仓库与已有改动，识别这是新游戏还是继续现有工程；复用有效代码并保留用户修改。
2. 写清M1范围、资源映射、首关地图标注和默认规则。普通实现细节按本文继续执行；只对会改变玩法或范围的关键歧义提问，并继续不依赖答案的工作。
3. 先形成加载素材、选择单位、合法移动、攻击、敌军行动与胜负的可玩闭环。
4. 加入对话、预测、动作、道具、经验和存档，完成界面与视觉校准。
5. 做规则测试和浏览器实玩，修复后交付运行命令、入口、验收证据及剩余问题。不要只输出设计方案、代码片段或目录树。

### 2. 验收清单

| 维度 | 必须验证的行为 |

按项目规范记录需求README、阶段决策、实际修改、验证与Git定位；没有提交就注明“尚未提交”。交付时区分“规则测试通过”“浏览器实玩通过”和“用户视觉验收”，不要将构建成功视为全部完成。
